# 本地视频同步播放设计

## 意图

Band Room 当前只能加载 Guitar Pro 曲谱。部分乐谱以视频形式存在，因此第一阶段增加本地视频播放源：主机从电脑选择视频文件，Band Room 服务端临时保存并向同一房间的设备提供流式读取；主机统一控制播放、暂停和跳转，成员设备自动跟随。视频声音只在主机播放，成员设备始终静音，避免多设备延迟造成回声。

本阶段不下载、代理或解析 Bilibili、抖音等网站视频，也不提供在线视频网址播放。

## 目标

- 主机可以在 Guitar Pro 曲谱和本地视频之间选择一种房间播放源。
- 视频上传不经过 WebSocket Base64 编码，不要求浏览器或服务端一次性把整个文件读入内存。
- 服务端支持浏览器按需读取和拖动所需的 HTTP Range 请求。
- 主机的播放、暂停和跳转继续以服务端房间时钟为权威并广播给所有成员。
- 主机视频正常输出声音；成员视频强制静音并自动跟随。
- 切换播放源、房间过期或服务端退出时清理临时视频。
- 维持现有局域网、无需账户、无需公网的产品特性。

## 非目标

- 不抓取、下载或转码任何第三方网站视频。
- 不在首版支持字幕、弹幕、播放列表或多视频编排。
- 不保证浏览器不支持的封装或编码能够播放。
- 不追求多设备音频采样级同步；成员端没有音频输出。
- 不改变“只有主机可以控制房间播放”的权限模型。

## 约束与默认选择

- 首版接收 `.mp4` 和 `.webm`；服务端同时校验扩展名、声明的 MIME 类型和有限的文件签名。编码是否可解码由浏览器 `<video>` 能力决定，失败时显示明确错误。
- 单个视频默认上限 2 GiB。该值作为服务端常量，后续可配置；上传前客户端先检查，服务端仍执行最终限制。
- 视频和 Guitar Pro 是互斥播放源。新来源成功加载后，旧来源才被替换并删除，避免失败上传清空当前排练内容。
- 房间号仍是读取房间内容的访问边界；写入和控制必须携带 `hostToken`。
- 不引入 ffmpeg。视频时长由浏览器读取元数据后报告，服务端保存经过范围校验的 `durationMs`；时长尚未知时允许加载但不做结束位置裁剪。

## 已考虑的方案

### 方案一：统一播放源适配器（采用）

房间公开一个互斥的 `source`，类型为 `score` 或 `video`。服务端播放时钟只依赖来源的可选时长；前端分别用 AlphaTab 和 HTMLVideoElement 实现相同的加载、播放、暂停、跳转与校准职责。

优点是同步协议只有一套，来源切换语义清楚，也为以后增加合法的在线嵌入来源保留边界。代价是需要把当前以 `score` 为中心的少量消息和渲染逻辑整理为来源模型。

### 方案二：在现有代码中增加视频条件分支

保留 `room.score`，另加 `room.video`，在每个消息和界面函数里判断当前类型。开发初期更快，但来源状态、清理和同步会分散在多个分支，未来增加在线视频时维护成本明显上升，因此未采用。

### 方案三：视频只在主机播放，成员只显示时间

实现最简单，也不需要成员读取视频，但不能满足“视频谱在每台设备同步查看”的核心需求，因此未采用。最终只保留其音频策略：声音仅在主机输出。

## 服务端设计

### 房间与公开来源模型

房间由 `score` 字段迁移为内部 `source`：

```js
{
  kind: 'score' | 'video',
  id: '<不可猜测的来源版本标识>',
  fileName: 'example.mp4',
  mimeType: 'video/mp4',
  size: 123456,
  durationMs: 180000,
  storagePath: '/private/path' // 永不发给客户端
}
```

曲谱来源继续携带现有的标题、速度、轨道和展开时间线。`publicSource()` 去除 `storagePath`。`room:joined` 返回 `source`；加载成功统一广播 `source:loaded`。来源发生变化时，服务端先暂停并把位置归零，然后广播新来源和新的播放状态。

为降低一次性迁移风险，内部可以保留现有曲谱解析函数，但其结果包入 `kind: 'score'` 来源。

### 视频上传

新增主机专用 HTTP 接口：

```text
POST /api/rooms/:roomId/video
Authorization: Bearer <hostToken>
Content-Type: video/mp4 | video/webm
Content-Length: <bytes>
X-File-Name: <encodeURIComponent 后的文件名>
```

请求体直接是文件字节。服务端将请求流写入 `videos/` 下的 `.upload` 临时文件，并在流式写入过程中累计字节数和检查上限。校验成功后原子改名并替换房间来源；请求中断、超限或校验失败时删除临时文件并保留原来源。上传响应返回公开来源，随后通过 WebSocket 向房间广播。

主机页面使用 `fetch` 直接发送 `File`，不再使用 `arrayBuffer()`、Base64 或 WebSocket。上传期间显示进度状态；首版若原生 `fetch` 无法提供可靠上传百分比，可以只显示“不确定进度”的上传状态，不为进度引入额外依赖。

### 视频流式读取

新增接口：

```text
GET /api/rooms/:roomId/video/:sourceId
```

接口仅在 `sourceId` 与房间当前视频来源匹配时响应，防止浏览器缓存或旧页面读取已经切换的文件。无 `Range` 时返回完整文件；合法单范围请求返回 `206`，并设置 `Accept-Ranges`、`Content-Range`、`Content-Length`、正确的 `Content-Type` 和 `Cache-Control: no-store`。非法或越界范围返回 `416`。使用文件流输出，不使用 `readFile()`。

### 视频时长登记

HTMLVideoElement 触发 `loadedmetadata` 后，主机通过受 `hostToken` 保护的 WebSocket 消息报告有限且为正数的 `durationMs`。服务端只在来源 ID 仍匹配时更新时长并广播来源元数据。成员读取到的时长可用于显示，但不具备修改权。

### 生命周期与错误处理

- 成功切换来源后删除旧曲谱或视频文件。
- 最后一位成员离开并超过现有宽限期后删除当前来源文件。
- `stopBandRoomServer()` 删除所有房间来源和未完成上传的临时文件。
- 上传失败返回中文 JSON 错误；播放器解码失败由前端显示“浏览器不支持此视频编码或文件已损坏”。
- 播放时钟以 `source.durationMs` 代替当前的 `score.durationMs` 做结束裁剪。

## 前端设计

### 来源选择与展示

主机的“曲谱”区域改为“排练内容”，提供两个清晰的输入：Guitar Pro 文件和本地视频。加载任一来源会替换房间当前内容。成员只看到当前来源，不显示上传控件。

视频来源显示原生 `<video playsinline preload="metadata">`：

- 主机：`muted = false`，使用统一的房间播放按钮，不暴露原生独立控制条，避免本地状态绕过服务端。
- 成员：设置 `muted = true`、`defaultMuted = true`、`volume = 0`，不提供解除静音入口；这也有利于浏览器允许自动播放。
- 视频支持现有全屏入口；曲谱仍使用当前 AlphaTab 全屏布局。

AlphaTab 只在曲谱来源下初始化或加载。视频来源下隐藏曲谱轨道选择、伴奏准备和曲谱渲染状态，显示视频加载/缓冲状态。主机播放视频不需要“准备伴奏”。

### 控制与同步

主机点击播放时，先在用户手势中调用视频 `play()`；成功后发送现有 `playback:control set-playing`。暂停和跳转继续走现有控制消息。若本地 `play()` 被浏览器拒绝，不改变服务端播放状态并显示错误。

每次收到 `playback:state` 时，客户端依据消息中的 `positionMs` 加上“消息到达后经过的本地时间”估算当前目标位置：

- 暂停状态：暂停播放器；偏差超过约 150 ms 时校正 `currentTime`。
- 播放状态且偏差大于 1 秒：直接跳转到目标位置。
- 播放状态且偏差在 250 ms 到 1 秒：成员端临时将 `playbackRate` 限制在约 `0.97–1.03` 之间追赶，回到阈值内后恢复 `1.0`。
- 偏差小于 250 ms：不操作，避免播放器抖动。
- 主机端不使用变速追赶，以免影响有声播放；主机出现明显偏差时直接校正。

阈值应集中为常量，并通过测试锁定状态转换。播放器处于缓冲状态时不反复调用 `play()`；恢复可播后立即按最新服务端状态校正。页面从后台恢复或 WebSocket 重连后也执行一次硬校正。

视频触发 `ended` 时，只有主机发送暂停并把位置固定到时长；成员等待服务端状态，避免多个设备竞争更新。

## 安全与隐私

- 文件名只用于展示，存储路径由服务端生成；禁止路径片段影响磁盘位置。
- 上传接口校验房间、主机令牌、长度、类型和文件签名；错误响应不暴露磁盘路径。
- 视频仍只保存在运行 Band Room 的主机数据目录，局域网设备只通过随机房间上下文读取。
- 法律与隐私页面补充说明：用户导入的视频会在房间内临时共享，用户必须确保有权使用该内容。
- 发布预检继续确保 `work/`、视频文件和临时上传不会进入安装包或仓库。

## 验证与验收

### 自动化测试

- 未授权成员不能上传视频或登记时长。
- MP4/WebM 上传成功；错误扩展名、MIME、签名、空文件、超限文件和中断上传失败且不替换旧来源。
- 完整读取、合法 Range、后缀 Range、非法多范围和越界 Range 的状态码及响应头正确。
- 切换曲谱/视频会暂停、归零、广播一次新来源并删除旧文件。
- 视频时长会限制播放位置并在结尾停止。
- 房间过期和服务端关闭会清理视频及临时文件。
- 现有曲谱上传、同步和权限测试继续通过。

### 手动验收

- 主机加载一个浏览器兼容的 MP4，手机和电脑成员均能开始播放并在拖动后重新对齐。
- 只有主机有声音，成员刷新、重连和退出全屏后仍保持静音。
- 网络短暂中断、视频缓冲和页面切到后台后能够恢复到最新位置。
- 加载不兼容编码时出现明确错误，不导致房间断线或服务端崩溃。
- 在 macOS 与 Windows 桌面包中验证大文件上传、拖动和应用退出清理。

## 实现者可自行决定的细节

- HTML 与 CSS 的具体排版，只要曲谱和视频来源状态清晰且移动端可用。
- 临时文件名、内部辅助函数名及来源 ID 的具体生成方式。
- 同步阈值在上述量级内的微调，但必须集中配置并由测试覆盖。
- 上传状态使用原生不确定进度或轻量的可测进度实现。
